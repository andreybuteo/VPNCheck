# Единый промпт-ТЗ для Codex: VPN Check

Ты — инженер-разработчик. Создай в текущей рабочей папке законченное локальное приложение **VPN Check** для Windows 11 x64. Нужна рабочая программа, а не макет интерфейса или план реализации. Прочитай применимые AGENTS.md, сохрани чужие изменения, затем реализуй, протестируй и собери приложение. Обычные технические решения принимай самостоятельно в рамках этого ТЗ. Не останавливайся после создания красивого фронтенда: сетевые проверки, история, настройки и экспорт должны действительно работать.

## 1. Задача и границы

Пользователь подключает VPN, запускает приложение, нажимает «Начать проверку» и видит доступность и задержки нужных сервисов: Autodesk Fusion, OpenAI/ChatGPT, Anthropic/Claude, Google, YouTube, Telegram, GitHub и инструментов разработки. Потом переключает VPN-сервер и сравнивает результаты.

Приоритеты: корректные измерения → щадящее поведение → простой сценарий использования → красивый компактный интерфейс. Не добавляй облачный backend, аккаунты, подписки, управление VPN, автозапуск Windows, службу, планировщик, сканирование портов или собственный браузер. Не меняй DNS, маршруты, прокси, firewall или настройки VPN операционной системы. Не требуй прав администратора.

Программа проверяет доступность контрольных узлов, а не гарантирует полноценную работу приложений. Доступность страницы YouTube не доказывает воспроизведение видео; доступность доменов Fusion — сохранение проекта; TLS к API — успешный вызов модели. Покажи это ограничение в справке и деталях результата. Не обещай нулевой риск блокировки.

## 2. Компактная архитектура

- Backend: Go, преимущественно стандартная библиотека. Используй установленную поддерживаемую версию и зафиксируй её в документации. Небольшие зависимости допустимы только по делу, с фиксированными версиями.
- Интерфейс: обычные HTML/CSS/JavaScript без React, Electron, npm-сборки и тяжёлой библиотеки графиков. Графики и иконки — локальные SVG/CSS. Все ресурсы встроить в executable через `go:embed`; никаких внешних шрифтов, CDN или аналитики.
- Один `VPNCheck.exe`: двойной щелчок запускает backend и открывает интерфейс в браузере по умолчанию. Python, Node.js, Docker и установка отдельного сервера пользователю не нужны.
- Слушать только `127.0.0.1` на свободном порту, не `0.0.0.0`. Для прогресса используй локальный SSE или другой простой механизм без перезагрузки страницы.
- Предусмотри явную кнопку «Завершить приложение», корректную отмену запросов и освобождение порта. Закрытие вкладки не должно притворяться завершением backend; объясни поведение.
- Настройки и последние 100 запусков — локальные JSON-файлы в `%LOCALAPPDATA%\VPNCheck`, запись атомарная, ошибка файла не должна уничтожать историю. SQLite не нужен. При отсутствии истории показывать пустое состояние.
- Ориентир: executable до 25 МБ, память backend в простое до 80 МБ, без учёта браузера. Это целевые показатели: измерь доступное и укажи фактические значения, не выдумывай их. Не применяй упаковщики executable ради размера.
- Раздели сетевой движок, классификацию результатов, хранилище и UI на несколько понятных модулей. Не создавай сложную платформу плагинов.

## 3. Пользовательский сценарий и интерфейс

Сделай аккуратный русскоязычный dashboard в стиле компактной инженерной утилиты: тёмная графитовая тема по умолчанию, светлая тема переключателем, спокойный бирюзовый акцент, тонкие границы, небольшие скругления. Системный шрифт, хороший контраст, единообразные отступы, цифры с табличной шириной. Без огромного баннера, декоративных спидометров, эмодзи вместо иконок и искусственных данных.

На одном основном экране:

1. Шапка: VPN Check, поле названия профиля, например «VPN — Германия», выбранный режим маршрута, кнопки «Начать проверку» / «Остановить».
2. Переключатель «Быстрая» / «Стабильность» и выбор сервисов; настройки спрячь в компактную боковую панель.
3. Сводка: сколько узлов проверено, сколько подтвердили TLS, сколько HTTP-ответов соответствуют профилю, сколько ошибок/ограничений, медиана времени установления защищённого соединения. Показывай знаменатель и тип проверки; разные типы не смешивать в один непрозрачный балл 0–100.
4. Сетка компактных карточек сервисов: название, понятный текстовый статус, задержка с названием метрики, количество проверенных узлов. Во время работы — очередь и текущий этап.
5. По нажатию карточки раскрывается таблица: адрес, роль, режим пробы, DNS/TCP/TLS/TTFB в мс, HTTP-код, фактическое семейство IP, итог. Ошибка раскрывается до понятного объяснения и технической причины. Неприменимые значения — «—», не нули.
6. Поиск и фильтры «Все / Проблемы / Доступны / Не проверены». Цвет обязательно сопровождать текстом или значком.
7. История и сравнение двух запусков, экспорт JSON/CSV, кнопка копирования краткого итога без чувствительных данных.

Интерфейс должен помещаться на 1366×768 без горизонтального скролла; длинные детали могут прокручиваться. На узком экране карточки перестраиваются. Предусмотри состояния: первый запуск, нет интернета, все ошибки, частичная проверка, отмена, cooldown, повреждённая настройка. Управление с клавиатуры и видимый фокус обязательны.

## 4. Проверки и метрики

Предусмотри два типа контрольных точек:

- `tls`: DNS → TCP 443 → TLS с SNI и штатной проверкой сертификата; затем корректно закрыть соединение. HTTP-запрос не отправлять. Это основной щадящий вариант для API и авторизации.
- `https`: один заранее заданный GET к небольшому публичному ресурсу; DNS, TCP, TLS и TTFB измерять на этом же запросе, а не делать отдельные дублирующие подключения перед ним. HEAD использовать только если поддержка конкретного endpoint подтверждена; не делать автоматическую пару HEAD → GET.

Для HTTPS используй события `net/http/httptrace`, для TLS-only — измерения этапов соединения. Используй монотонное время. Определения:

- DNS — время фактического локального разрешения имени, если оно наблюдалось; кэш ОС не очищать.
- TCP — время успешного подключения к фактическому peer; у прокси это прокси, а не конечный сервер.
- TLS — время рукопожатия с проверяемым HTTPS-хостом. Время CONNECT/прокси учитывать отдельно, не приписывать TLS.
- TTFB — от начала конкретного HTTPS-запроса до первого байта ответа, включая предшествующие сетевые этапы. Не складывать его повторно с DNS/TCP/TLS.
- Время до готовности TLS — от начала пробы до завершения проверки сертификата; пригодно для сравнения одинаковых узлов и режимов.
- Общее время пробы и прочитанные байты — отдельно. Если тело ограничено лимитом, это не «время полной загрузки сайта».

Сохраняй фактический адрес peer, протокол HTTP, результат сертификата, этап сбоя, тип ошибки, UTC-время, режим маршрута, endpoint ID и версию профиля. Для Happy Eyeballs учитывай несколько попыток соединения корректно; не суммируй параллельные попытки как последовательные. В пределах запуска не переиспользуй соединения так, чтобы DNS/TCP/TLS следующего узла случайно исчезли; не переносить активные подключения между запусками после смены VPN.

Режимы:

- «Быстрая»: одна проба каждого включённого endpoint. Прогресс обновляется по мере завершения. При нормальной сети ориентир — несколько десятков секунд; не обещать фиксированные 10 секунд при тайм-аутах.
- «Стабильность»: пользователь выбирает до 5 узлов; по 3 пробы с интервалом не менее 10 секунд между пробами одного узла, с теми же лимитами. Показывай min/median/max, количество успехов и размах задержки; помечай малую выборку. Долю неудачных запросов не называй потерей сетевых пакетов, а разброс TLS/HTTP-задержки — измеренным сетевым jitter.
- По умолчанию семейство IP — Auto; сохраняй реально использованное. Отдельные IPv4-only/IPv6-only разреши для системного маршрута как явно выбранный режим нового запуска. Не дублируй автоматически все проверки ради обеих семей. За прокси не показывай семейство peer как доказанное семейство конечного сервера.

ICMP, traceroute, HTTP/3, MTU, WebSocket/SSE до внешних сервисов и speedtest в первую версию не включать. Схему результатов оставь расширяемой, но никаких неработающих кнопок «скоро».

## 5. Маршрут: VPN и прокси

Это критически важная часть, а не второстепенная настройка.

- «Системный маршрут / TUN»: приложение идёт через текущую маршрутизацию Windows, без application-level proxy. Это не режим «обойти VPN».
- «Прокси»: пользователь явно задаёт HTTP CONNECT или SOCKS5 адрес. Для SOCKS5 предпочитай удалённое разрешение имени, без скрытого локального DNS-запроса к целевому домену. На старте достаточно прокси без авторизации; неподдерживаемую авторизацию отклоняй с объяснением, не сохраняй пароль в JSON.
- Прочитай доступные настройки прокси Windows и переменные окружения только для подсказки. Покажи обнаруженное пользователю и предложи применить поддерживаемый адрес. Не считай `ProxyFromEnvironment` чтением системного прокси Windows. PAC/WPAD можно явно не поддерживать в v1; сообщи об этом, если они обнаружены.
- В шапке всегда показывай реально применённый режим. Если обнаружен системный прокси, а выбран системный маршрут, объясни, что путь браузера и программы может различаться.
- При ошибке прокси не переключайся незаметно на прямой маршрут. Все внешние запросы, включая проверку IP, обязаны использовать выбранный режим. В режиме прокси ненаблюдаемые DNS/удалённые TCP-метрики помечать «не измерено через прокси».
- Не утверждай автоматически, что VPN включён или весь трафик защищён. При split tunneling маршруты разных сервисов могут различаться.

Опциональный переключатель «Показать внешний IP» по умолчанию выключен. При включении — один запрос к документированному сервису определения IP в начале запуска и один в конце, через тот же маршрут, с общими ограничениями. Укажи провайдера и факт передачи ему запроса. Страна/ASN — только если выбранный источник реально отдаёт их без ключа; иначе «нет данных». Не внедряй отдельную геобазу. При изменении IP предупреди, что условия запуска менялись; одинаковый IP не считать доказательством неизменного маршрута. В публичном экспорте IP скрывать по умолчанию.

Реестр можно редактировать через настройки и импортировать/экспортировать JSON без пересборки. Перед применением импорт полностью валидировать, при ошибке сохранять прежнюю конфигурацию. Пользовательские точки — только публичные HTTPS-хосты на 443, без credentials в URL.

## 7. Щадящее поведение и безопасность

Это обязательные ограничения backend, а не только выключенные кнопки:

- Никаких внешних запросов при открытии интерфейса: только после нажатия «Начать». Нет фонового мониторинга, обхода CAPTCHA, платных API-вызовов, авторизации, cookies браузера, токенов и чтения чужих учётных данных.
- Не более 4 одновременных проб глобально, одной на hostname. В пределах одной группы сервиса начала проб разносить минимум на 1 секунду. Один активный запуск на процесс; повторное нажатие не создаёт дубликаты.
- Cooldown между запусками минимум 60 секунд от начала предыдущего. Скользящий потолок на hostname: 12 проб в час; действует во всех режимах, включая повтор/семейство IP, и сохраняется при обычном перезапуске. При исчерпании пропускать узел и показывать время ожидания. Это наша осторожная настройка, а не официальная универсальная квота сервисов.
- Тайм-аут всей пробы 10 секунд, TCP и TLS — максимум по 4 секунды в рамках общего дедлайна. Отмена закрывает активные операции и не запускает новые; тайм-ауты действуют также для прокси и чтения тела.
- Для HTTP: максимум 64 КиБ прочитанного тела, ограничение заголовков и времени чтения; никаких картинок/скриптов со страницы и больших загрузок. Учти сжатие и сетевую буферизацию: лимит тела приложения — не обещание строго такого же количества байтов на проводе.
- Не следовать HTTP-редиректам автоматически. Сохранить код и безопасно отображённый Location; для нужного конечного адреса использовать отдельную проверенную точку. Не повторять запрос автоматически после ошибки или неподдерживаемого метода.
- При `403` или CAPTCHA остановить пробы этого hostname до конца запуска. При `429` также сохранить cooldown: учесть `Retry-After` в обеих формах и известные rate-limit reset headers; если их нет — минимум 15 минут. Не сбрасывать ограничение при смене профиля VPN. `403` сам по себе не объявлять баном IP.
- Проверка сертификата обязательна. Не устанавливать доверенные корневые сертификаты, не отключать TLS-проверку и не изменять защиту Windows.
- Локальный API: проверка Host/Origin, сессионная защита и CSRF-защита изменяющих операций, запрет произвольного CORS. Внешняя веб-страница не должна суметь запустить тест, прочитать историю или выключить приложение. SSE тоже защищён.
- Валидировать целевые адреса, блокировать loopback, private, link-local, multicast и metadata IP в IPv4/IPv6, в том числе после DNS-разрешения и перед подключением. Не допускать DNS rebinding. Исключение — только явно настроенный пользователем адрес самого прокси. При удалённом DNS в прокси документировать предел видимости и защиты клиента.
- Не выполнять URL через shell. Ошибки/названия/Location выводить как текст, не HTML; защитить CSV от formula injection. В логах и экспортируемом результате не сохранять cookies, токены, proxy credentials и полные HTTP-тела. Query-параметры пользовательских URL редактировать/скрывать в публичном отчёте.
- Все тайм-ауты, лимиты и отмена должны работать и в тестах. Никаких бесконечных retries.

## 8. Честная классификация результатов

Храни раздельно транспортный результат и HTTP-результат. Для каждой точки показывай одну понятную итоговую подпись, не теряя фактический код:

| Наблюдение | Что показывать |
| --- | --- |
| TLS-only успешно | «TLS доступен; работа приложения не проверялась» |
| HTTPS и ожидаемый ответ | «Контрольный ресурс доступен» |
| DNS / TCP / TLS failure | Соответствующий этап и конкретная ошибка |
| `401` | «Сервер ответил; требуется авторизация»; не «API работает полностью» |
| `403` / CAPTCHA | «Запрос отклонён / требуется проверка; причина не установлена» |
| `429` | «Ограничение частоты; повтор после …» |
| `3xx` | «Перенаправление» и адрес; не ошибка сети |
| Неожиданный `404` / `405` | «Контрольный URL или метод не подходит»; не «VPN не работает» |
| `5xx` | «Ошибка сервера/шлюза»; соединение и TLS могли быть успешны |
| Отмена / локальный лимит / disabled | Отдельное состояние, не сетевая ошибка |

В карточке группы показывай состав результата: например «2/3 узла доступны, 1 ответ отклонён». Не делай сервис зелёным только по одному успешному узлу при других ошибках. Жёлтый «медленно» допустим по документированному настраиваемому порогу одной и той же метрики; это локальная эвристика, не SLA сервиса. Серый — не проверено/недостаточно данных.

## 9. История, сравнение и экспорт

- Каждый запуск хранит название профиля, время, выбранный маршрут и его настройки без секретов, версию приложения, снимок endpoint-конфигурации, режим, реальные результаты и статус завершения.
- Сравнение по стабильным ID и совпадающим параметрам пробы. Показывай статусы «было → стало», абсолютную и процентную разницу одной метрики, только если оба числа измерены и база ненулевая. Если тип пробы/URL/семейство IP изменились — предупреди о несопоставимости. Различие маршрутов показывать, это и есть предмет сравнения VPN.
- Последние результаты можно смотреть без интернета; интерфейс не запускает сетевую проверку при открытии истории.
- JSON — версионированная машиночитаемая схема, неизвестные метрики `null`. CSV — UTF-8 с BOM и понятные заголовки для Excel, одна строка на отдельную пробу. Экспорт отменённого запуска допустим с соответствующей пометкой.
- Краткий текстовый итог должен быть удобен для отправки администратору. Внешние IP, локальные proxy-адреса и чувствительные параметры по умолчанию скрыты; включение подробных сетевых данных — отдельный явный выбор при экспорте.

## 10. Тестирование и выдача

Сначала составь короткий рабочий план, затем выполни его до рабочего результата. Не расширяй MVP необязательными функциями.

Обязательные автоматические тесты — локальные и воспроизводимые, без зависимости от доступности зарубежных сайтов:

- классификация `200`, `301`, `401`, `403`, `404`, `405`, `429`, `500`, DNS/TCP/TLS errors;
- правильное разделение таймингов, отсутствие измерения → `null`, параллельные события трассировки;
- общий дедлайн, зависшее тело, медленный прокси, отмена очереди и активного запроса;
- лимиты параллельности, повтора, HTTP-тела, `Retry-After`, сохранение cooldown;
- отсутствие редиректа и скрытого обхода прокси, корректные пробы через локальный тестовый прокси;
- валидация URL, запрет private/metadata и rebinding, Host/Origin/CSRF, HTML/CSV injection;
- история, повреждённый JSON, атомарная запись, сравнение и экспорт без секретов.

Для тестовых серверов допустим отдельный внедряемый test-only механизм разрешения loopback; в production API такую настройку не предоставлять. TLS-тесты использовать с тестовым доверенным CA, не с глобальным отключением проверки сертификатов.

Запусти `go test ./...`, `go vet ./...`, а где доступно — race detector. Проверь UI вручную или доступной браузерной автоматизацией: запуск/остановка, фильтры, детали, настройки, история, сравнение, экспорт, обе темы и размер 1366×768. Изолированный demo/test-режим разрешён только для QA и явно помечен; обычный запуск не показывает подставные успешные результаты.

Реальные запросы к сервисам при разработке — только минимальный smoke-test через тот же ограничитель, если сеть и полномочия среды это позволяют. При сетевом запрете не обходи его: тестируй локально и честно укажи, что проверка с компьютера пользователя ещё нужна. Сборка Windows на Linux не равна проверке запуска Windows.

Выдай:

1. Полный исходный код, встроенный реестр, тесты и `go.mod`/`go.sum` при наличии зависимостей.
2. `VPNCheck.exe` и компактный ZIP-релиз, если сборка в среде доступна; иначе рабочий код и точные воспроизводимые команды сборки. Не заявляй о собранном файле, которого нет.
3. Короткий `README.md` на русском: запуск, завершение, выбор TUN/прокси, добавление адресов, хранение/экспорт данных и ограничения методики.
4. Скрипт `build.ps1`, SHA-256 готового executable, фактический размер и краткий отчёт о выполненных тестах. Если бинарник не подписан, укажи это; не предлагай отключать защиту Windows.

Критерий готовности: пользователь без среды разработки запускает один файл, нажимает одну кнопку, получает реальные понятные результаты, может остановить тест, сравнить другой VPN-профиль и выгрузить отчёт. Все заявленные элементы UI работают; программа остаётся небольшой и не создаёт агрессивной нагрузки.

Технические опорные источники; актуальность деталей проверь при реализации:

- События сетевых измерений: [Go httptrace](https://pkg.go.dev/net/http/httptrace).
- Поведение стандартного HTTP-клиента и прокси: [Go net/http](https://pkg.go.dev/net/http#ProxyFromEnvironment).
- Лимиты и реакция на отказ API: [GitHub REST API rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api). Эти правила нельзя механически переносить на остальные сервисы.
